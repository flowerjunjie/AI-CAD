## 一、对项目理解

仔细阅读贵司项目说明后，我认为这是一个极具战略价值且时机恰好的赛道——AI Agent + 垂直行业（建筑设计）正在从概念走向落地，而施工图深化这一环节，正是AI最有可能产生实际价值的切入点。

### 1.1 核心判断

贵司对项目的定位非常准确：

- **方案阶段人类主导，AI负责后半段规则明确的施工图深化** —— 这个边界划分决定了项目的可行性。当前AI的能力边界适合做"辅助"而非"替代"，重复性、规则化的工作完全可以由AI承担。
- **不要求第一版覆盖五个专业** —— 避免了贪大求全的典型失败模式，务实且可控。
- **知识资产由贵司提供** —— 历史图纸和规范条文是AI系统最稀缺的领域知识，这是核心竞争力，不是技术团队需要从头建设的。

### 1.2 我的理解

这个项目的本质不是"AI画图"，而是**"AI辅助施工图深化Agent"**。关键区别在于：前者要求AI从零创造（目前做不到），后者是基于人类方案做规则化、重复性的延伸（完全可行，价值明确）。

## 二、GitHub全球技术调研结论

为制定技术方案，我对GitHub上相关开源项目进行了系统性调研。

### 2.1 核心发现

| 项目名称 | Stars | 与本项目的相关性 |
|---------|-------|----------------|
| **Autocad-MCP** | 71 | 最直接参考：AutoCAD MCP服务器，122个工具，双引擎(COM+ezdxf) |
| openlintel | — | 端到端家装设计自动化，概念验证性质 |
| VedaCAD/v-code | 1 | LLM驱动CAD几何生成的学术实验 |
| cADR | 17 | AI驱动的架构决策记录，偏文档 |
| Autodesk APS Revit MCP | — | 欧特克官方Revit AI工具包，证明大厂布局此方向 |

### 2.2 关键结论

**目前全球范围内，没有成熟的"AI施工图深化Agent"开源方案。** 这既是挑战，也是先行者优势。

最接近本项目技术路线的是 **Autocad-MCP**（71⭐，MIT协议），它提供了三个关键启示：

1. **双引擎架构是当前最稳方案** —— COM接口控制AutoCAD + ezdxf读写DWG
2. **MCP（Model Context Protocol）是AI Agent与CAD交互的标准范式** —— 已被Autodesk官方认可
3. **这条技术路线已被证明可行** —— 不是纯学术想象，已有可运行的原型

### 2.3 技术趋势判断

- Autodesk在2025-2026年已开始布局MCP生态，**AI+CAD是行业共识方向**
- 国内快手可灵、阿里Wan、腾讯HunyuanVideo在生成式AI领域进展迅速
- 但**AI+结构化工程图纸**（而非图片/视频）仍是蓝海，精度和可靠性要求更高，竞争者更少

## 三、技术方案概要

### 3.1 架构原则

> **规则引擎保准确，LLM保灵活，人在回路保可控。**

- **规则引擎**：将规范条文（防火间距、疏散宽度、面积计算等）写成可执行代码，这部分不依赖LLM，保证准确性
- **LLM层**：负责理解设计师的自然语言意图、处理规则之外的模糊场景
- **人在回路**：每个关键节点暂停等待确认，AI不直接出图，最终成果由设计师审核签字

### 3.2 技术栈选型

| 层级 | 技术 | 选择理由 |
|------|------|---------|
| 桌面应用 | Electron + React | 跨平台，可嵌入AutoCAD插件，生态成熟 |
| CAD引擎 | ezdxf (Python) + COM接口 | ezdxf读DWG，COM写AutoCAD——双引擎最稳 |
| Agent框架 | LangGraph | 支持可中断/可观察的执行流，适合人在回路 |
| LLM | MiniMax/Kimi/GLM | 中文规范理解强，API成本低，数据不出境 |
| 知识库 | ChromaDB（本地部署） | 轻量，无需外部服务，符合设计院数据安全要求 |
| 规则引擎 | 自定义DSL + 程序校验 | 规范条文写成代码，不依赖LLM做逻辑判断 |

### 3.3 实施路径

```
Phase 0（第1-2周）：技术预研 + 环境搭建
  → DWG读写Demo、COM接口验证、LLM接入、RAG知识库雏形

Phase 1（第3-8周）：建筑专业MVP
  → 住宅套型施工图：墙体生成→门窗插入→尺寸标注→规范初检
  → 每步人工确认，验证人机协作流程

Phase 2（第9-14周）：规则引擎完善
  → 规范DSL化、批量校验、修改联动、版本对比

Phase 3（第15-22周）：第二专业接入
  → 选择给排水或电气中规则最明确的一个专业

Phase 4（第23周起）：多专业协调 + 团队搭建
  → 碰撞检测、统一坐标系、招聘3-5人核心团队
```

### 3.4 交付承诺

| 时间 | 交付物 |
|------|--------|
| 第1周 | 开发环境就绪，技术选型确认，DWG读写Demo跑通 |

## 四、风险识别与应对

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| DWG解析精度不足 | 中 | 高 | 双引擎（ezdxf读+COM写），复杂情况fallback人工 |
| LLM规范理解错误 | 高 | 中 | 规则引擎不依赖LLM——规范写成代码，LLM只做意图理解 |
| 多专业协调复杂度高 | 高 | 高 | 第一版不做全专业协调，先做单专业，第二阶段再接入 |
| 设计师使用意愿低 | 中 | 高 | MVP阶段让用户参与，每周迭代，让他们有掌控感 |
| 生成结果不符合验收标准 | 中 | 高 | 所有输出必须经过人工确认环节，AI不直接出图 |

## 五、我的建议

### 5.1 MVP切入点：住宅套型施工图

建议选择**住宅套型施工图**作为第一个MVP场景，理由：

- 规则最明确（国标住宅设计规范条目清晰，容易验证）
- 图纸量适中（不会太大导致验证周期过长，也不会太小缺乏代表性）
- 验收标准清晰（设计师一眼能看出对错，便于快速迭代）
- 市场需求最大（住宅是建筑设计中最普遍的类型）

### 5.2 技术路线核心判断

**不建议第一版就做五个专业。** 每个专业的规范体系差异巨大，同时攻关会分散资源。一个专业做深做透，验证了技术路线和团队协作模式后，再横向复制到第二专业，边际成本会显著下降。

### 5.3 团队配置建议

第一版3-5人核心团队：
- 技术负责人（我）：技术路线、核心Agent框架、CAD引擎对接
- 后端工程师×1-2：规则引擎、RAG知识库、API层
- 前端/桌面端工程师×1：Electron应用、CAD可视化、UI交互
- CAD开发×1（可选）：ezdxf/COM深度封装

招聘优先级：AutoCAD二次开发经验 > Agent框架经验 > 桌面端经验。
