## 一、问题理解与核心判断

### 1.1 你们在做什么

先说底层逻辑——这不是一个简单的"AI画图"工具，而是一个**工业级 AI Agent 系统**，要解决的是：

> **设计院的核心痛点**：方案阶段设计师花大量时间创意思考，但施工图深化阶段 80% 的时间在做重复性、规则明确的工作（标注、材料表、规范检查、多专业协调）。这一部分本该由 AI 来做。

### 1.2 关键约束（必须对齐）

| 约束 | 含义 | 技术影响 |
|------|------|---------|
| 桌面端 | 必须装在设计师电脑上，不能依赖云端 | 本地推理 + 离线可用是硬需求 |
| 人机协作 | 方案阶段人类主导，AI 接手后半段 | 不是全自动，是"人在回路"的 Agent |
| 五专业分阶段 | 不要求第一版全部覆盖 | MVP 必须选一个专业做深，不能贪大求全 |
| 知识由公司提供 | 不要求我懂建筑 | 重点是 AI 架构，不是建筑行业知识 |
| 前期亲自写代码 | 不是纯管理岗 | 技术负责人必须是能写核心代码的人 |

### 1.3 核心判断

**这个项目的本质不是"AI生成CAD"，而是"AI辅助施工图深化 Agent"。**

关键区别：
- "AI生成CAD" = 让AI从零画图（目前做不到，精度不够）
- "AI辅助施工图深化" = 基于人类方案，AI做规则化、重复性工作（完全可行，有明确价值）

**这就是你的抓手——聚焦后半段，别碰前半段。**

3. AutoCAD/Revit的AI集成刚刚起步（Autodesk官方在2025-2026年才开始推MCP方案）
4. **这意味着：你们是先行者，没有竞品可以直接对比，技术路线需要自己探索**

### 3.2 关键技术选型

| 层级 | 技术 | 选择理由 |
|------|------|---------|
| **桌面框架** | Electron + React | 成熟生态，可嵌入AutoCAD/Revit插件，跨平台 |
| **CAD引擎(核心)** | ezdxf (Python) + COM接口 | ezdxf读DWG，COM写AutoCAD——双引擎方案最稳 |
| **Agent框架** | LangGraph 或自建状态机 | LangGraph支持可中断/可观察的执行流，适合人在回路 |
| **LLM** | 国内优先（MiniMax/Kimi/GLM） | 中文规范理解强，API成本低，数据不出境 |
| **RAG知识库** | ChromaDB + 向量嵌入 | 轻量本地部署，无需外部服务 |
| **规则引擎** | 自定义DSL + 程序校验 | 规范条文写成可执行规则，不依赖LLM做逻辑判断 |
| **图元/素材库** | 本地SQLite + 文件存储 | 设计师的历史图纸作为向量检索库 |
| **多专业协调** | 统一坐标空间 + 冲突检测算法 | 各专业输出同一坐标系下的DWG，检测碰撞 |

### 3.3 Agent 执行流程设计

```
用户输入方案 (PDF/图片/简要描述)
        │
        ▼
┌──────────────────┐
│  意图理解 Agent   │ ← LLM解析：这是什么类型的项目？哪些专业需要？
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  方案结构化 Agent │ ← 提取：建筑面积、层数、功能分区、主要构件
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  任务分解 Agent   │ ← 拆成：墙体绘制→门窗标注→尺寸标注→材料表→规范检查...
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  CAD执行 Agent   │ ← ezdxf/COM操作：逐条生成图元
│  (人机协作节点)   │    每完成一个子任务，暂停等待人类确认
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  规则校验 Agent   │ ← 规范检查：防火间距、疏散宽度、面积计算...
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  多专业协调 Agent │ ← 检测：结构与建筑碰撞、管线穿梁...
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  成果输出 Agent   │ ← 生成DWG/PDF/报表
└──────────────────┘
```

**关键设计原则**：每个 Agent 节点都是"可中断、可编辑、可追溯"的——人类可以随时介入修改，AI 从当前状态继续。

## 四、分阶段实施计划

### Phase 0：技术预研（第1-2周）

| 任务 | 产出 | 验证标准 |
|------|------|---------|
| 搭建 Electron + React 桌面框架 | 可运行的空壳应用 | 能打开AutoCAD文件并显示内容 |
| 验证 ezdxf 读写 DWG | DWG读写Demo | 能读取DWG实体列表，能写入简单图元 |
| 验证 COM 接口调用 AutoCAD | COM调用Demo | 能通过Python控制AutoCAD打开/保存/绘制 |
| 搭建 LLM 接入层 | API适配层 | 能调通国内至少2个API，延迟<3s |
| 搭建 RAG 知识库雏形 | ChromaDB + 规范解析Demo | 能问答"疏散走道最小宽度是多少" |

**里程碑交付物**：一个能打开DWG、显示内容、回答简单规范问题的桌面原型。

### Phase 1：MVP — 建筑专业施工图深化（第3-8周）

**切入点选择**：以"住宅套型施工图"为MVP场景——规则明确、图纸量可预估、验收标准清晰。

| 模块 | 功能 | 优先级 |
|------|------|--------|
| 方案输入 | 接收PDF/图片方案，自动识别户型轮廓 | P0 |
| 墙体生成 | 基于识别结果生成墙体图元（含厚度标注） | P0 |
| 门窗插入 | 按规范自动插入门窗图块（带编号） | P0 |
| 尺寸标注 | 自动生成轴线标注、洞口标注 | P0 |
| 材料表生成 | 自动生成门窗表、墙体材料表 | P1 |
| 规范初检 | 检查：门宽≥0.9m、窗台高度≤0.9m等硬性规则 | P0 |
| 人工确认界面 | 每个步骤暂停，设计师确认/修改 | P0 |

**验证方式**：找1-2个真实住宅户型，跑通全流程，统计人工工时减少比例。

### Phase 2：规则引擎 + 多轮迭代（第9-14周）

| 模块 | 功能 |
|------|------|
| 规则 DSL | 将规范条文写成可执行代码（如：卫生间门宽≥0.8m） |
| 规则编辑器 | 设计师可以自行添加/修改规则，不用改代码 |
| 批量校验 | 全图纸一次扫描，输出问题清单 |
| 修改联动 | 修改一处，关联标注自动更新 |
| 版本对比 | 每次修改生成diff，可回溯 |

### Phase 3：第二专业接入（第15-22周）

选择**给排水**或**电气**中规则更明确的一个专业接入——这两个专业的规范条目化程度高，容易验证。

### Phase 4：多专业协调 + 团队搭建（第23周起）

| 模块 | 功能 |
|------|------|
| 统一坐标系 | 建筑/结构/水电在同一坐标空间 |
| 碰撞检测 | 自动检测管线穿梁、插座撞梁等冲突 |
| 团队权限 | 多设计师协作，改动冲突检测 |
| 招聘计划 | 后端工程师×2、CAD开发×1、前端×1 |

## 五、关键风险与应对

### 5.1 技术风险

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| DWG解析精度不足 | 中 | 高 | 双引擎：ezdxf(读) + COM(写)，复杂情况fallback到人工 |
| LLM对规范理解错误 | 高 | 中 | 规则引擎不依赖LLM——规范写成代码，LLM只做意图理解 |
| 多专业协调复杂度高 | 高 | 高 | 第一版不做全专业协调，先做单专业，第二阶段再接入 |
| 桌面端性能 | 中 | 中 | CAD文件大时异步处理，UI不阻塞 |

### 5.2 业务风险

| 风险 | 应对 |
|------|------|
| 设计师不愿意用 | MVP阶段就让用户参与，每周迭代，让他们有掌控感 |
| 规则太细导致覆盖率低 | 先做20%的规则覆盖80%的场景，逐步扩展 |
| 生成结果不符合验收标准 | 所有输出必须经过人工确认环节，AI不直接出图 |

### 5.3 我的判断：最大风险是"贪大求全"

**不要试图第一版就做五个专业。** 理由：

1. 每个专业的规范体系差异巨大，同时攻关会分散资源
2. 第一个专业的MVP验证成功，才能建立团队信心和公司投入意愿
3. 建筑专业的施工图深化已经足够复杂，足够验证技术路线

**建议策略：一个专业做深做透，再横向复制。**

## 八、面试时可以说的话（核心观点）

### 8.1 对项目的理解

> "我理解你们的核心诉求不是'让AI完全替代设计师'，而是'让AI帮设计师把80%重复性工作干了，设计师只做20%需要判断的决策'。这个定位非常准确——目前AI的能力边界也支持这个分工。"

### 8.2 技术路线判断

> "我建议的技术路线是：**规则引擎为主，LLM为辅**。为什么？因为施工图的核心是'准确'，不是'创意'。规范条文是可以写成代码的确定逻辑，这部分不该依赖LLM。LLM的价值在于理解设计师的自然语言意图，以及处理那些规则之外的模糊场景。这样设计的好处是：出错率可控，且可以逐步替换LLM为更好的模型而不改核心逻辑。"

### 8.3 关于分阶段策略

> "五个专业同时启动是典型的多项目并行失败场景。我建议用一个真实项目跑通建筑专业全流程，验证技术路线可行后，再把同一套框架复制到第二专业。这样每个新专业的边际成本会显著下降。"

### 8.4 关于桌面端的必要性

> "桌面端的核心价值是**离线+安全+集成**。设计院的图纸涉及商业机密，不能传云端。AutoCAD是设计师每天用的工具，必须无缝集成。这两个需求决定了不能用纯Web方案。"

## 十、总结

### 核心结论

1. **GitHub上没有可以直接复用的完整方案**——你们是先行者，技术路线需要自己探索
2. **最接近的技术方向是 Autocad-MCP + ezdxf 双引擎方案**
3. **核心架构：规则引擎保准确 + LLM保灵活 + 人在回路保可控**
4. **分阶段策略：先做一个专业做深做透，再横向复制**
5. **第一版团队3-5人，重点招AutoCAD二次开发经验的人**

### 一句话总结

> "这个项目最难的不是技术，而是找到技术与设计工作流的契合点——让AI做AI擅长的事（规则化、重复性工作），让人做人擅长的事（判断、决策、创新）。技术路线我已经想清楚了，现在需要的是团队和验证。"
