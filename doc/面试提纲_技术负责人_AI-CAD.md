# 第二部分 · 两个医疗项目举证（硬实力，必问必答）

> 这两段是整场面试的承重墙。技术负责人岗，对方一定问"你做过什么系统"。你要让医疗系统替你说话——它比 AI-CAD 难管的点，一个不少。

## 2.1 RuoYi-Vue_ICU · 重症监护临床信息系统

【口播 · STAR 结构，念得出来】

> "第一个是 ICU 临床信息系统，基于 RuoYi-Vue 框架，现在在生产环境跑的是 v3.0.0。"
>
> **S（背景）**："三甲医院 ICU 的病区，原来体征数据靠护士手写，告警靠人盯，文书靠事后补。我接手时的判断是：这套东西不能自建，框架太重、合规更难。"
>
> **T（任务）**："要做出一个临床决策支持系统，能上床旁，PHI/PII 不能漏，数据要审计。"
>
> **A（我做的）**：
> - "选型上，我选了 RuoYi-Vue 而不是自己搭 Spring Cloud。理由很直接：ICU 系统 80% 的难点在临床业务和合规，不在中台。框架自带权限、审计、多租户，把合规基线省下来，团队火力全部砸在临床模块。"
> - "拆模块上，我把系统分成 20 多个业务模块。这里举几个有代表性的：icu-alert 负责告警，icu-decision 是临床决策支持，icu-monitor 单独成模块存时序数据，icu-fhir 做 HL7 FHIR 标准集成。为什么时序数据（生命体征采样）不塞进 MySQL，要单独一个 monitor 模块？因为一条 ICU 床一小时上千条采样，普通关系库的写吞吐和保留策略根本扛不住，我把它当独立数据存储来设计。"
> - "合规上，PHI/PII 的脱敏和审计日志是 v3.0.0 的硬门槛。上线前过了医疗专家团审计，评级是 SAFE TO DEPLOY，PHI/PII 保护 100% 通过。"
>
> **R（结果）**："交付时配了 124 条以上 SQL 迁移脚本、37 个部署脚本、138 个项目文档、K8s 部署配置。高可用上，后端有 actuator 健康检查，Redis 上线要跑 PONG 验证，编排走 K8s。团队留存到现在没掉人。"

【为什么强调这几个决策】面试官听到"为什么选 RuoYi""为什么时序数据独立模块""为什么 FHIR"，就知道你不是照着框架文档抄的——你是做过取舍的人。技术负责人岗要的就是这个。

## 2.2 Obstetric ICU · 产科重症监护平台（设计→落地完整一条线）

> "第二个是产科重症监护平台，这个我做得更完整，从 PRD 一直做到能部署的版本。"

【口播】

> **设计层**（PRD v2.1）："定位是产科重症一体化平台。临床侧做五件事：多设备对接、AI 辅助诊疗、五色分级预警、闭环输液、一键抢救协议。业务背景是围产期风险最高的场景——子痫前期、羊水栓塞、产后大出血、HELLP 综合征，这些病抢的就是分钟级的时间。我写 PRD 时明确了一个原则：预警不能是'提醒'，要能直接进抢救流程。"
>
> **落地层**（W13B 工程版）：
> - "后端拆成 15 个 Spring 微服务。按业务能力分：vital-signs 管体征采集，warning-engine 是预警引擎，infusion 是闭环输液，rescue 是抢救协议，ai-assist 做辅助诊疗，ctg 专门做胎心监护，再加 patient、ward-dashboard 这些。"
> - "设备网关单独用 Go 写了一个——oicu-device-gateway-go，出 linux 和 exe 双产物。"
> - "数据层用 MySQL 存业务、Redis 做会话、Kafka 做事件总线、ZooKeeper 做协调、TDengine 存时序。可观测性上接了 OpenTelemetry 全链路，部署走 Docker Compose。"

【三处架构决策，每个都是加分点】

> - **"为什么体征用 TDengine，不用 MySQL？"** —— "生命体征是一天几十万到上百万条的时间序列数据，普通 MySQL 在时间维度上的压缩、按时间窗口查询、数据保留策略都不行。TDengine 按超级表设计，天然为时序优化。这不是炫技，是存储模型跟数据形状匹配。"
> - **"为什么设备网关用 Go 不用 Java？"** —— "网关这层的活儿是：多路设备协议解析、长时间稳定运行、内存占用要低。Go 的 GC 是 Stop-the-world 但停顿短、内存可预测、部署单二进制。Java 网关跑几路串口设备没问题，但床旁设备数量上去之后，内存和启动时间的差距会显出来。"
> - **"Kafka 在'预警→抢救'里干什么？"** —— "预警引擎发现五色分级触发，不直接调抢救模块。它发事件到 Kafka，rescue 服务订阅这个事件开抢救协议，ai-assist 订阅同一个事件生成诊疗建议。解耦的好处：告警级别调整不用改代码，新增订阅方（比如科研数据自动采集）不改既有链路。这就是产科场景能'自动归档科研数据'的底层。"

## 2.3 三十秒串联（把两段经验接到 AI-CAD）

【口播】

> "我做过两套医疗系统，一个是通用 ICU，一个是产科 ICU，从 PRD 做到能部署。这两个系统比 AI-CAD 更难管的点，正好是这个岗位要的能力：一是异构设备要稳——产科那套 Go 网关处理过十几路设备，这套经验直接用在 CAD 设备解析和多格式读写上；二是合规和安全是硬门槛——医疗有 PHI/PII，设计院有图纸保密，思路一样，都是'数据不出境、本地可审计'；三是多人协作的实时状态——预警事件用消息总线驱动，跟多专业协调 Agent 的状态同步是一个问题。所以 AI-CAD 的技术难度，我已经在医疗系统上付过学费了。"

# 第三部分 · AI-CAD 技术论证（你的专业，主场）

> 这部分对方一定会问。你要主动讲，别等问——主动讲是主导权。

## 3.1 项目定位（必须先对齐，再谈技术）

【口播】

> "先说我对这个项目的理解，确认我们口径一致。"
>
> "AI-CAD 不是让 AI 画图。画图是前端创作的事，现在做不到，也不该做。AI-CAD 是**辅助施工图深化的 Agent**：人类出方案，AI 接后半段——标注、材料表、规范检查、多专业协调，这些规则化、重复性的活。边界这么划，价值才立得住。"
>
> "所以架构上有三个原则：**规则引擎保准确，LLM 保灵活，人在回路保可控。**规则引擎是把规范条文写成代码，不依赖概率模型；LLM 只做意图理解和规则外的模糊场景；每个关键节点停下来等设计师确认，AI 不直接出图。"

## 3.2 四个核心技术判断（每个都是'为什么 + 怎么做'）

> 这四条是技术含金量的全部。对方问哪条，展开哪条。但**至少前两条要主动讲**。

**判断一：规则引擎和 LLM 必须分家**

【口播】

> "规范是确定逻辑，LLM 是概率模型。'户门宽度不小于 0.9 米'这种条文，写成一行 if 就完了，让 LLM 算，它可能给你 0.8、0.9、0.95，哪个都对不上验收。所以规则引擎独立成模块，规范全用 DSL 写成可执行代码，LLM 不碰逻辑判断。LLM 的价值在另一头：设计师说'把这个客厅改大一点'，这种自然语言意图 LLM 能懂，规则引擎不能。两者分家，出错可控——哪边出错就修哪边，不用重训模型。"

**判断二：ezdxf（读 DWG）+ COM 接口（写 AutoCAD）双引擎**

【口播】

> "CAD 文件读写这事，我用双引擎。ezdxf 是纯 Python，读 DWG 不用装 AutoCAD，跨平台，设计意图是把它当只读解析层。COM 接口是 Windows 专属，能写 AutoCAD，输出的是 AutoCAD 原生格式，设计师打开没有兼容问题。这样分的好处：设计院的电脑没装 AutoCAD 时，ezdxf 照样能解析；装了 AutoCAD 时，COM 能直接写回去。哪头出精度问题，另一头补。不是二选一，是读写分离、互为 fallback。"

**判断三：桌面端 Electron，不选 Web**

【口播】

> "设计院图纸是商业机密，不能传云端。Web 方案天然有数据出境风险，这条在合规上就过不去。其次，AutoCAD 是设计师每天的工具，AI 必须能嵌进它的工作流，不能让他们开一个新标签页。Electron 桌面端，离线可用，数据本地，API Key 本地存。这三条是硬约束，不是偏好。Web 方案在这套约束下没有出路。"

**判断四：LangGraph，不是普通 LLM 调用**

【口播】

> "人在回路要的是**可中断、可观察、可编辑**的执行流。普通 LLM 调用是'进一句、出一句'，中间状态不可见，设计师没法介入。LangGraph 把 Agent 流程定义成图，每个节点是一个可暂停的检查点，人在这个节点改完数据，Agent 从当前状态继续，不用重跑。设计师要改哪步，就停在哪个节点。这是人在回路的底层机制，不是装饰。"

## 3.3 项目当前真实进度（举证"我做出过东西"）

【口播 · 这段必须说，是你最有底气的部分】

> "我不是来画饼的。AI-CAD 我现在跑到 Phase 0，全链路已经通了。刚在本地跑过一键脚本，实打实的数据：
>
> 规则引擎注册了 **30 条规范**（21 条 ERROR、6 条 WARNING、3 条 INFO），实测一条 0.6m 的户门直接命中「户内门宽度≥0.9m」的违规。户型解析从 100 ㎡ 的 JSON 样本（7 个功能区、7 门 5 窗）生成 12 个 CAD 任务，LangGraph Agent 端到端跑完，出 DWG 文件，检测到 2 条规范违规（门宽 + 门窗碰撞）。
>
> 规则引擎不是几个 if，是有 DSL 编译器，规范写成声明式条目，引擎负责校验，违规分 ERROR / WARNING / INFO 三档。四专业（结构、给排水、暖通、电气）的 extractor 写完了，跟上游走 attrs 契约，数据格式不匹配直接报错，不会静默错。
>
> 测试 26 个文件，四专业的 e2e 和 DSL 边界测试都有。
>
> LLM 接入做了统一抽象层，支持 5 个适配器（Agnes / MiniMax / Kimi / GLM + 基类），走配置切换，不锁死任何一家。
>
> 我说的不是 PPT。这是能跑的代码，我下一步要在这个底座上搭团队。"

【为什么要主动说进度】技术负责人岗最怕"想法很好、代码一行没写"。这句话直接把你从 PPT 选手里摘出来。进度不完美没关系，**真实**比完美值钱。

> **现场演示弹药**（如果对方有电脑或允许你操作）：`output/preview.png`（440×742 户型渲染图）+ `output/report.html`（一键生成的运行报告）是现成的证据，不用临场跑。面试时一句"我可以现场打开看"，比任何 PPT 都有说服力。跑 `python run.py --no-llm` 是 10 秒出图，不需要联网。

## 3.4 高频技术题（对方大概率会问，答得利落）

# 第四部分 · 风险预判（技术负责人必考"你想过风险吗"）

# 第五部分 · 技术负责人软技能（对方问管理能力时）

> 技术负责人岗，"能不能带人"是必考。不要讲愿景，讲动作。

## 5.1 技术选型决策——电力交易拆微服务

> "电力交易那个系统，我做的最重的一次决策是拆微服务。拆之前想清楚了三件事：
>
> 第一，拆的依据是业务边界，不是'微服务更现代'。8 个微服务，商品、交易、结算、风控各有独立生命周期，拆了之后单模块升级不碰别的。
>
> 第二，什么时候引入 Redis 和消息队列：先跑通单体，压测找出瓶颈，哪个接口响应时间顶不住了才拆到缓存和异步。不是上来就堆架构。
>
> 第三，团队能不能接住。我带的是 12 人，前端 3、后端 5、移动端 2、测试 1。为什么这么配：电力交易后端是核心，5 人分八个微服务刚好每人两到三个；前端 3 人管交易台、管理后台、移动端三端；移动端单独留 2 人是给后续交易 App 做的预留。测试 1 人加 2 个开发跑自动化，是我判断测试不能是独立职能，得有开发懂业务才能写出有效用例。"

【为什么这样讲】选型的决策过程比结论重要。"先压测再拆""测试要跟开发配合"——这些是踩过坑才有的话。

## 5.2 团队管理——医疗系统的质量关

> "医疗系统我管的和质量管理最严。上线前每个模块过医疗专家团审计，PHI/PII 保护必须 100% 通过。代码层面，review 是必须的，我自己 review 每个 PR 的核心逻辑。新人 onboarding 有固定文档，30 天内能独立跑任务。这套流程下来，开发效率反而比没规范化之前提了 50%——规范化不是减效率，是减返工。"

## 5.3 跨部门——让建筑师参与迭代

> "设计院场景最难的：技术要做，但设计师不写代码。我的做法是每周设计评审，但不是让设计师看 Demo，而是让设计师说'这一步我要看到什么结果'，再决定 AI 在哪停。规则库开放给设计师自己写条目，他不用懂 Python，用 DSL 写，我负责让 DSL 足够简单。设计师有控制感，才愿意用。"

## 5.4 0 到 1 vs 接手

> "两个我都干过。0 到 1 最难的不是技术，是判断什么时候不做什么。接手一个已有系统最难的是知道哪些是债务、哪些是资产。医疗系统我是接手 RuoYi 框架重新设计临床模块——框架是中台，临床是新的，这个组合比从零快 30%。"

# 第六部分 · 我要问对方的 8 个问题（技术负责人的格局）

> 面试最后一定会问"你有什么想问我们的"。这 8 个题，**挑 4 个问**，别全问。每个问你都要知道"问这个能挖出什么"。

**1. 团队现状**

> "这个岗位到位，带几个人？现在技术团队什么背景？"
>
> 【为什么问】挖的是：我是搭新团队还是接手有人团队的。有没有 CAD 开发、有没有 Agent 经验。直接决定我的第一周要做什么。

**2. 图纸知识资产**

> "历史图纸库和规范条文库，现在有多少？质量怎么样？能不能直接给 RAG 用？"
>
> 【为什么问】这是 AI-CAD 的命门。没有干净的图纸和规范，RAG 就是空的。问这个，我同时判断对方是真想做系统还是想做融资故事。

**3. 验收标准**

> "施工图做出来了，谁判定它是对的？验收红线在哪？"
>
> 【为什么问】写进了规则才算数，没写进规则的 AI 出了错要谁负责。这个答案决定了 MVP 的范围边界。

**4. 数据合规边界**

> "设计院图纸的保密级别到什么程度？LLM 用国内还是国外？API Key 存储有没有红线？"
>
> 【为什么问】这是桌面端方案的依据。对方如果对数据出境没概念，说明合规还没落地，我的第一周要补这个课。

**5. MVP 选哪个户型**

> "第一个可演示版本，你们想选什么类型的户型？多久要看到第一个闭环？"
>
> 【为什么问】MVP 节奏和范围，直接定我的优先级。"住宅套型施工图"还是"商业综合"，规则库完全不一样。

**6. 决策权边界**

> "技术负责人能拍板的边界在哪？向谁汇报？预算够不够我组团队？"
>
> 【为什么问】挖汇报线和预算。没有决策权的技术负责人，就是高级 IC，不做决策的人不需要技术负责人岗。

**7. 技术底座**

> "团队有没有 AutoCAD 二次开发、DWG 处理的经验？还是从零开始？"
>
> 【为什么问】有 AutoCAD 开发经验的人，招聘优先级第一。没有的话，我的第一阶段重点是补人，不是写代码。

**8. 为什么现在做**

> "这个方向知道 Autodesk 在推 MCP 吗？你们判断现在做而不是等它成熟的理由是什么？"
>
> 【为什么问】挖对方的行业判断力。如果连 Autodesk MCP 都不知道，说明团队认知有断层，我的职责里要加"教育团队"。如果答得清楚，说明有行业认知，我来了只需要执行。

# 第七部分 · 薪资谈判 + 收尾话术

## 7.1 薪资怎么谈

> 对方问薪资时：
>
> "我期望的薪资范围是 X 到 Y。但更我想谈的是这个岗位的责任边界——能不能带人、决策权、第一阶段预算。薪资可以在边界清楚之后再谈，边界不清楚，数字定了也是虚的。"

【为什么要这样】技术负责人薪资谈的是**决策权 + 团队规模 + 预算**，不是月薪。先把边界谈清楚，薪资自然水到渠成。

## 7.2 压力题应对（问你的部分）

| 问题 | 应对 |
|---|---|
| **"你为什么离开现公司？"** | "电力交易上线后进入稳定运营期，我的核心职责是维护 5000 并发，没有新的架构决策空间了。我想做一个从 0 到 1 的项目，AI-CAD 的窗口对。" |
| **"薪资预期多少？"** | 见 7.1，先谈边界再谈数字。 |
| **"你一个人能扛多少事？"** | "我扛的是技术决策和团队搭建，不是写所有代码。第一周我自己把核心 Agent 框架跑通，验证路径可行，再招人扩团队。一个人扛到团队成型，这是我能扛的范围。" |
| **"项目黄了谁负责？"** | "技术上我负责，商业上你们负责。我负责的是：按节奏出可演示版本，每个节点可验收。如果版本到了、验收标准没达标，那是技术债，我认。如果验收标准本身模糊、商业逻辑没跑通，那是产品定义问题，不全是技术的锅。" |

## 7.3 收尾话术（背熟，最后一句定印象）

> "我做过电力交易、做过两套医疗系统，从设计规范做到生产部署。AI-CAD 的技术难度，我已经在医疗系统上踩过坑了——异构设备、合规安全、实时状态同步，我都有现成的方案。你们现在最需要的，不是 AI 团队，是一个能在第一周把核心链路跑通、在第二个月搭起团队的人。我就是来干这个的。你们什么时候可以出第一个 offer？"

【为什么这么说】收尾不是表决心，是**把球踢回去**。"你们什么时候可以出第一个 offer"——这句话让对方知道：你在选他们，不是在等他们选。技术负责人离场，要留下"这个人可以立刻上手"的信号。
