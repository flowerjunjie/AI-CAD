## ADR-001: CAD 引擎双策略

**状态**: 已接受  
**日期**: 2026-09-09  
**背景**: 需要在跨平台环境下读写 DWG 文件

**决策**: 采用 ezdxf (Python) + COM 接口双引擎策略

**理由**:
- ezdxf 是纯 Python 实现，无需 AutoCAD 安装，适合读取和跨平台场景
- COM 接口是与 AutoCAD 原生兼容的写入方式，保证输出格式标准
- 双引擎互为 fallback，提升系统鲁棒性

**后果**:
- 增加了一层抽象，调试复杂度上升
- Windows 平台功能最全，Linux/macOS 仅支持 ezdxf 基础功能
- 需要维护两套接口

**替代方案**:
- 仅用 ezdxf: 写入兼容性差，不符合设计院交付标准
- 仅用 COM: 仅限 Windows，不符合跨平台需求

## ADR-002: Agent 框架选型

**状态**: 已接受  
**日期**: 2026-09-09  
**背景**: 需要支持"人在回路"的可中断执行流

**决策**: 选用 LangGraph 作为 Agent 框架

**理由**:
- 原生支持可中断、可观察的执行流
- 状态管理成熟，适合多步骤复杂流程
- 社区活跃，文档完善

**后果**:
- 引入 LangGraph 依赖，增加学习成本
- 与 LangChain 生态深度绑定

**替代方案**:
- 自建状态机: 开发成本高，复用性差
- LangChain: 缺乏人在回路的原生支持

## ADR-003: LLM 本地化部署

**状态**: 已接受  
**日期**: 2026-09-09  
**背景**: 设计院对图纸数据安全有严格要求

**决策**: 所有数据本地处理，LLM 调用通过国内 API

**理由**:
- 图纸涉及商业机密，不能上传云端
- 国内 LLM (MiniMax/Kimi/GLM) 对中文规范理解更好
- API 成本低，延迟可控

**后果**:
- 需要稳定的网络连接
- 离线场景功能受限

**替代方案**:
- 本地部署大模型: 硬件成本高，推理速度慢

## ADR-004: RAG 知识库本地化

**状态**: 已接受  
**日期**: 2026-09-09  
**背景**: 需要存储和检索建筑规范条文

**决策**: 使用 ChromaDB 本地部署向量数据库

**理由**:
- 轻量级，无需外部服务
- 支持本地持久化，符合安全要求
- API 简洁，易于集成

**后果**:
- 大数据量下性能可能不足
- 需要定期备份

**替代方案**:
- Milvus: 功能强大但部署复杂
- Pinecone: 需要云端，不符合安全要求
